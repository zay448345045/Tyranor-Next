# 应用层页面切换性能优化方案

## 1. 范围与目标

本方案只覆盖 `app` 模块的 Jetpack Compose 页面层，不修改 `engine` 模块或任何游戏引擎运行逻辑。

目标：

- 消除主页面 Tab 切换期间不必要的逐帧重组。
- 避免跨多个 Tab 时在动画途中组合无关页面。
- 降低液态玻璃导航在页面移动期间的离屏录制与实时模糊成本。
- 将游戏库、最近游戏和快捷启动统一为 Activity 级状态，避免相邻页面各持有一份数据。
- 移除页面首次组合中的游戏库同步读取。
- 控制封面并发解码，稳定 LazyGrid 首次进入时的主线程与 RenderThread 压力。
- 保持现有页面结构、主题、水平切页语义和液态玻璃静态视觉不变。

## 2. 优化前基线

测试设备：`24053PY09C`，分辨率 `1236 × 2750`，刷新率 `120Hz`，当前导航样式为 `liquid_glass`。

| 路径 | P50 | P90 | P95 | P99 | GPU P90 |
|---|---:|---:|---:|---:|---:|
| 首页 → 游戏 | 18ms | 30ms | 32ms | 73ms | 5ms |
| 游戏 → 设置 | 18ms | 38ms | 150ms | 150ms | 5ms |

120Hz 单帧预算约为 `8.33ms`。现状中位帧超过两个刷新周期，跨页切换的 P95 达到 `150ms`。

## 3. 根因与实施项

### 3.1 主 Tab 切换

现状：

- `HorizontalPager` 与独立 `selectedIndex` 形成两个状态源。
- 从首页直接进入设置时，Pager 动画会经过中间页面，并在动画途中创建页面内容。
- `beyondViewportPageCount = 1` 会在首页阶段提前组合游戏页和加载封面。

实施：

- 使用单一 `selectedIndex` 驱动 `Transition`，以 `graphicsLayer` 执行水平位移与透明度动画。
- 四个 Tab 只在 MainActivity 首次创建时组合一次，后续切换不再重建游戏网格和 Miuix 设置页。
- 隐藏页 `alpha = 0`，同时清除语义，并在 `Initial` 指针阶段抢先消费事件；动画完成前目标页也不响应触摸。
- 跨 Tab 直接移动起点和终点，中间页虽然常驻但透明度始终为 0，不经过屏幕。
- 搜索词、滚动位置和页面任务由常驻组合自然保留，不再依赖 `SaveableStateHolder` 恢复。
- 代价是冷启动首次组合增加约 `180ms`（实测 890ms → 1070ms），换取后续每次 Tab 切换不再出现设置页重建长帧。

### 3.2 液态玻璃导航

现状：

- 页面内容通过 `layerBackdrop` 整页录制。
- 导航底板与焦点胶囊同时执行实时 blur，底板还执行 lens。
- `focusX` 在组合阶段读取，焦点动画每帧都会重组整个导航栏。
- 导航项列表和回调在父级重组时重复创建。

实施：

- 动画 State 只在 `offset`/`graphicsLayer` 阶段读取，跳过 Composition。
- 流体拉伸值在 `graphicsLayer` 内计算。
- 只保留导航底板一层 backdrop，blur 从 24dp 降为 12dp，并移除高成本 lens。
- 焦点胶囊改为主题色半透明流体层，不再执行第二套 blur 管线。
- `layerBackdrop` 与底板效果链常驻，不在动画首尾反复挂载/编译。
- 导航项列表提升为稳定的顶层常量。
- 尺寸和中心坐标只在数值实际变化时写入 State。

### 3.3 页面状态与主线程读取

现状：

- 首页和游戏页各自持有游戏库派生状态。
- `EngineScanner.loadGames/loadRecentGames/refreshQuickLaunch` 在组合初始化器中同步执行。
- 页面间通过缓存版本号和手动写回进行同步。

实施：

- 新增 Activity 级 `MainLibraryViewModel`。
- 使用 `StateFlow<MainLibraryUiState>` 统一提供游戏库、最近游戏、快捷启动和加载状态。
- ViewModel 在 `Dispatchers.IO` 加载持久数据。
- 更新、删除、扫描结果和快捷启动变更统一写入 ViewModel，再持久化。
- 持久化命令经 `Channel.UNLIMITED` 单消费者 FIFO 执行，保证快速连续操作按用户顺序落盘。
- 以 revision 阻止较早的刷新/写入结果覆盖较新的乐观 UI 状态。
- 游戏更新按“实际变化字段”合并到最新磁盘对象，避免重命名覆盖同时完成的封面刮削。
- 扫描任务迁移到 `viewModelScope`，离开游戏 Tab 后继续执行并保持扫描状态。
- ViewModel 直接观察全局刮削任务，游戏页不在组合树时也会更新首页数据。
- MainActivity 恢复前台时从存储刷新一次，接收游戏运行后产生的最近记录。
- 页面使用 `collectAsStateWithLifecycle`，避免不可见 Activity 继续无意义收集。

### 3.4 列表与封面

现状中 LazyGrid/LazyColumn 已普遍提供稳定 key，列表结构不是首要瓶颈。剩余问题主要是冷封面并发解码和数据稳定性。

实施：

- 为 `ScanGame` 标记 `@Immutable`，帮助 Compose 跳过未变化卡片。
- 为固定类型 Lazy 项补充 `contentType`。
- 限制封面同时解码数量，避免首次显示时大量 IO/Bitmap 工作同时完成。
- 相同封面 URI 使用按键 Mutex 串行；首个卡片离开组合被取消后，等待者可继续重试。
- 保留现有 24MB LRU 缩略图缓存与按尺寸采样。
- 缓存最近游戏时间文本，避免行重组时反复创建格式化器。

### 3.5 性能保障

实施：

- 保留 Debug 单元测试和 Debug APK 构建回归。
- 增加主页面状态 ViewModel 的行为测试。
- 用同一台实机、同一导航样式、同一 Tab 路径执行 `gfxinfo reset` 对比。
- 检查首页、游戏、引擎、设置四页均可到达，快速连续点击后最终页面与选中 Tab 一致。

## 4. 验收标准

- 首页 → 游戏：P95 明显低于优化前 `32ms`，不出现 `70ms+` 长帧。
- 游戏 → 设置：P95 从 `150ms` 降至不高于 `50ms`，不再在动画中组合中间页。
- GPU P90 不高于优化前 `5ms`。
- 页面切换期间不再因 `focusX` 变化触发导航栏逐帧重组。
- 冷启动预组合游戏页时，封面解码最多两路并发，不出现无上限 Bitmap 任务洪峰。
- 快捷启动、最近游戏、游戏删除、封面更新、扫描结果在首页与游戏页保持一致。
- 默认导航和液态玻璃导航均可正常切换。
- 所有单元测试、Debug 编译和 APK 安装通过。

### 6.3 优化后帧耗时

测试口径：同一台 120Hz 实机、液态玻璃导航、页面预热后，每条路径独立执行三轮
`gfxinfo reset → 点击目标 Tab → 等待 1 秒 → framestats`。下表使用三轮各百分位的中位数，
避免选择最好的一轮；GPU 同样取三轮 P90 中位数。

| 路径 | P50 | P90 | P95 | P99 | GPU P90 |
|---|---:|---:|---:|---:|---:|
| 首页 → 游戏（优化前） | 18ms | 30ms | 32ms | 73ms | 5ms |
| 首页 → 游戏（优化后） | 11.6ms | 21.3ms | 25.2ms | 65.6ms | 3.1ms |
| 游戏 → 设置（优化前） | 18ms | 38ms | 150ms | 150ms | 5ms |
| 游戏 → 设置（优化后） | 12.5ms | 21.7ms | 26.4ms | 62.0ms | 3.8ms |

改善幅度：

- 首页 → 游戏：P50 `-35.8%`、P90 `-29.1%`、P95 `-21.3%`、P99 `-10.2%`、GPU P90 `-37.6%`。
- 游戏 → 设置：P50 `-30.7%`、P90 `-42.9%`、P95 `-82.4%`、P99 `-58.7%`、GPU P90 `-25.0%`。

三轮单次最大帧范围：

- 首页 → 游戏：`26.9–86.9ms`；此前中间实现每轮必现 `160–328ms` 的玻璃/页面重建长帧。
- 游戏 → 设置：`37.7–63.9ms`；此前中间实现每轮必现 `207–410ms` 的设置页重建长帧。

120Hz 下 P50 仍高于严格 `8.33ms` 单帧预算，Debug 构建也不是最终发布性能上限；但主要长尾已经
从百毫秒级稳定尖峰收敛到 64ms 左右，且所有关键百分位和 GPU P90 均优于优化前基线。
